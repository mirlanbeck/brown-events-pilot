# BEVN-002: API documentation (Swagger/OpenAPI)

## Что сделали и что получилось

Все 12 эндпоинтов описаны в Swagger UI (`/swagger`): описание, параметры, все коды ответов
с пояснением, когда какой возникает (включая 404/415/500), пример тела запроса и пример ответа.
Источник — XML-комментарии в контроллерах и моделях, `[ProducesResponseType]`, примеры
через Swashbuckle.AspNetCore.Filters, общее описание API в `Swagger/ApiDocumentation.cs`.
Поведение API не менялось: проверено фильтром диффа (в контроллерах и моделях — только
комментарии и атрибуты) и тестами.

Работа шла итерациями, и каждая проверка находила что-то новое:

1. План → ок → реализация. Агент сверил коды ответов с кодом и выяснил, что `400` API не отдаёт
   вообще (нет `[ApiController]`), поэтому документировать его не стал.
2. Проверки на живом API (одноразовый Postgres, не моя dev-база) нашли дефекты, которых не было
   в BEVN-001: после одной FK-ошибки все записи падают с 500 до перезапуска; упавший PUT
   частично применяется.
3. Внешние инструменты (Redocly, Schemathesis, openapi-typescript) нашли неточности уже в самой
   спецификации: даты без часового пояса не проходят формат `date-time`, `null` во вложенных
   объектах и даже элементами вложенных массивов, нет `operationId`/`servers`.
   После исправлений Schemathesis: 9178 запросов без расхождений со схемой.
4. Слепой тест: отдельный агент получил только копию swagger.json и написал по нему клиент
   и ответы на 13 контрольных вопросов. Все ответы верные, но он нашёл, что примеры ответов
   не совпадают с примерами запросов, а при разборе всплыло, что утверждение «без `status`
   в PUT будет 500» неверно — статус тихо сбрасывается в `UPCOMING`.
5. Самый серьёзный дефект: ответы с сущностями обрываются после `200 OK` (глубина графа > 32)
   уже на демо-данных плюс пара записей; один ответ — 66 МБ. Описан в «Known issues».

DoD из issue #3: все 4 пункта закрыты; пункт про фронтендера подтверждён слепым тестом.

## Решения агента

- .NET SDK локально не было — агент собирал и запускал проект в контейнере `dotnet/sdk:6.0`
  вместо установки в систему; для проверок поднимал отдельный Postgres без volume
  и API на отдельном порту, compose-стек и dev-базу не трогал.
- Не стал вешать `[Produces]`/`[Consumes]`, хотя это стандартный способ: они меняют поведение
  (415/406). Вместо этого фильтр, который правит только документ.
- Задокументировал найденные баги как «Known issues (temporary)», а не исправлял — задача
  только про документацию; исправления — отдельный issue.
- Отказался от OpenAPI 3.1: в .NET 6 / Swashbuckle 6.5 его нет, переход требует обновления .NET.
  Цена — 4 предупреждения Redocly, которые остались осознанно.

## Где вмешался руками

- Потребовал план и своё «ок» до изменения кода; коммиты, push и PR — только после
  отдельного подтверждения.
- Спросил «мы всё учли?» — агент нашёл пропуски в плане (пункт DoD про фронтендера,
  проверка в Docker, «Try it out»).
- Спросил, какие решения агент принял на допущениях (assumptions) — он сам перечислил, где мог ошибиться,

- Остановил агента, когда он начал сам ставить npm-пакет; установил Python, Schemathesis,

- Решил: документация на английском; «Known issues» оставить в Swagger временно.

## Освоенные уроки

- Всегда сверять были ли "assumptions" агента, и стараться перепроверять решения принятые на основе данных допущений.

## Что сделал бы иначе

# BEVN-003: Technical debt audit

## Что сделали и что получилось

`docs/tech-debt-audit.md`: 54 находки (8 High, 29 Medium, 17 Low), бэкенд и инфраструктура — 41, фронтенд — 13
(было 51; три добавил слепой аудит, см. ниже).
Категории: надёжность, производительность/ORM, блокирующие вызовы, корректность, безопасность, конфигурация,
контракт API, тесты, фронтенд. У каждой находки — место (файл:строка), описание, severity, исправление,
сформулированное под NestJS (EXT-150), и пометка, как она подтверждена: запросом, в BEVN-002, кодом или это вывод.
Три обязательные области (async, загрузка связей ORM, CORS) вынесены в отдельный раздел с итогом по каждой.

Порядок работы: чтение issue/шаблона PR/devlog/architecture → план → моё «ок» → чтение всего кода →
проверки на изолированном стенде (отдельные Postgres и API в Docker, порт 5099; compose и dev-база не тронуты).
Код приложения не менялся.

Что дали проверки запросами (нового по сравнению с BEVN-001/002):

- Singleton `DbContext` — не теоретическая проблема: три параллельных запроса страницы конференции
  на свежем процессе — два `500` в 6 раундах из 6.
- N+1 в цифрах: 19–22 SQL на один GET, ответ на 2 сессии содержит все конференции и сессии базы (438 повторяющихся объектов), список из 3 спикеров — 376 КБ.
- Mass assignment: одним `POST /api/conferences` создались регистрация со статусом `VIP`, участник, сессия и спикер.
- Регистрация: 4 регистрации одного участника при лимите 1; при ошибке FK остаётся участник без регистрации.
- Логирование EF не подключено вообще: настройка SQL-логов в `appsettings.Development.json` мертва.
- CORS: preflight с чужого origin разрешён, но без credentials — поэтому Medium, а не High.

Слепой аудит (проверка полноты): отдельный агент только на чтение получил копию кода вне репозитория — без `docs/`
и без Swagger-описаний известных дефектов (коммит до BEVN-002; что логика с тех пор не менялась, проверено диффом) —
и текст задачи, но не наш документ. Результат: 48 находок, около 40 совпали, все High — совпали, расхождений
severity больше чем на уровень нет. Новое от него — 3 находки (нет `CancellationToken`, страница сессии не проверяет
конференцию из URL, статус конференции не зависит от дат) и 6 дополнений к существующим; всё перепроверено по коду
и внесено. Одно его утверждение (SQL с email пишется в прод-логи) опровергнуто нашим замером. Только у нас остались
находки, полученные запросами: обрыв ответа после `200`, обнуление полей в `PUT`, мёртвые логи EF.
Хэш состояния репозитория до и после совпал.

## Решения агента

- SQL считал по логу самого Postgres (`log_statement=all`), а не по логам EF — и так выяснилось, что логи EF не работают.
- Перед каждым замером перезапускал API: Singleton-контекст кеширует данные, и на «прогретом» процессе
  N+1 и параллельные ошибки не видны (повторный GET — 0 SQL).
- Сам нашёл ошибку в своём скрипте перезапуска (убивал сам себя, старый процесс оставался) — первые замеры
  были на «грязном» процессе; переделал перезапуск, пересоздал базу и снял все цифры заново на чистых демо-данных.
- Сам нашёл расхождение в сводке документа (было написано 48 находок, по факту 51) и исправил.
- Самопроверка по моей просьбе: ссылки и якоря проверены скриптом (ошибок нет); по содержанию исправлено 5 мест,
  главное — рекомендация по CORS для NestJS: ловушка не `*`, а `origin: true` + `credentials` (отражение любого origin).
  Остальное — точность формулировок: что измерено, а что выведено (механизм «отравления» контекста, подсчёт объектов).
- По моей просьбе добавил в аудит раздел «Как воспроизвести» (стенд + 7 проверок с ожидаемым результатом) и прогнал
  его в точности как написано. Первый прогон завис на час: в Git Bash отключённая конвертация путей ломала `curl`
  (`-o /dev/null` → код 23, бесконечное ожидание). Агент нашёл причину, исправил раздел, добавил ограничение
  ожидания; второй прогон — все 7 проверок совпали с ожидаемым. Без прогона в документ ушли бы неработающие команды.
- Документ на русском, как `architecture.md`; находки BEVN-002 вошли в аудит с пометкой «✔ BEVN-002», без повторного
  воспроизведения, кроме тех, где нужна была новая причина (отравление контекста — перепроверено).

  что ошибка выглядит как сетевая, а не как `500`, — это попало в аудит (CFG-3).
- Обновил страницу ещё раз и опроверг прогноз агента («после F5 загрузится — данные уже в кеше»): упали регистрации.
  Оказалось, из кеша отдаётся только поиск по id, а списки всегда идут в БД — гонка возможна при любом открытии
  страницы, не только после перезапуска. Формулировку REL-1 исправили.
- Снял в DevTools → Network: `registrations 500` при «Failed to fetch» на странице (ответ без CORS-заголовков),
  3 preflight на 3 GET, `sessions` 213 КБ на 2 сессии — три пункта аудита получили подтверждение в браузере.
  В Console — прямое подтверждение: `blocked by CORS policy: No 'Access-Control-Allow-Origin' header`.
- Согласился на раздел «Как воспроизвести» после того, как агент объяснил, что, сколько времени и что нужно.

## Освоенные уроки

- Кеш/состояние процесса может скрывать дефекты: на «прогретом» API N+1 и гонки не видны. Замер надо делать
  на чистом состоянии и знать, что именно «чистое».
- Проверочный скрипт тоже может врать: первые цифры были на старом процессе. Признак проблемы был в логе
  («address already in use») — его стоит читать, а не только итоговые числа.
- Конфигурация, которая выглядит рабочей (уровни логов EF), может не действовать вообще — проверять по факту.
- Прогноз агента «как поведёт себя система» — тоже утверждение, которое надо проверять: одно обновление страницы
  опровергло его объяснение про «прогретый» процесс.
- Слепой аудит и замеры дополняют друг друга: независимый взгляд нашёл то, что мы пропустили при чтении кода,
  а замеры опровергли его вывод, сделанный только по конфигу.

## Что сделал бы иначе

- Сразу заложил бы в план «чистое состояние перед каждым замером» и проверку, что стенд действительно перезапустился.
- Добавил бы нагрузочную проверку (например, k6/bombardier) — голодание пула потоков и рост памяти остались выводом.
- Проверил бы фронтенд в браузере на изолированном стенде, а не только статически.
- Запустил бы слепой аудит параллельно с основным, а не после: дешевле сравнить два списка сразу.

# EXT-110: CI на GitHub Actions

Кеш NuGet — через `actions/cache`, npm — через `setup-node`; на втором прогоне оба попали в кеш.
`.gitlab-ci.yml` удалён; 7 ссылок на него в аудите (CFG-4, SEC-7) переведены на постоянные ссылки на коммит `717c5bb`.

Разбор старого пайплайна по джобам — в описании PR #16 (пункт DoD):

- перенесены restore/build/test бэкенда и install/build фронтенда;

## Решения агента

- До любых изменений прогнал те же команды локально на текущем коде — чтобы заранее знать, что CI не упадёт из-за кода.
