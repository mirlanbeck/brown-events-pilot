## 2. Принципы

1. **Фронтенд не меняется: ноль диффа в `frontend/`.** Это и есть доказательство DoD-2. Всё, что фронтенд читает, остаётся
   совместимым; что он не читает — может меняться по аудиту.
2. **Противоречия DoD/аудита/фронтенда решены поштучно** (раздел 3), каждое отступление от «чистого» исправления — строкой в PR.
3. **Исправить, а не перенести**: эталон — источник поведения, а не стиля; дефектное поведение эталона не воспроизводится.
4. **Подтверждено / предполагаю**: каждое предположение имеет проверку в плане (раздел 14).

### 4.2 Структура `backend/`

.NET-код удаляется в этом PR (остаётся в истории, `e95142d`); новый код — в `backend/`, пути compose и CI те же.

## 5. HTTP-контракт

### 5.1 Успешные ответы

- Голые объекты и массивы, без конверта. Списки упорядочены по `id`.
- `GET`, `PUT` → `200`. `POST` → `201` с созданным ресурсом в той же форме, что и `GET`.
- `Location` (MNT-2 Fix): `POST /api/conferences` → `/api/conferences/{id}`; `POST /api/conferences/{id}/sessions` →
  `/api/sessions/{id}`. Спикер и регистрация — без `Location` (нет `GET` одного ресурса, новых эндпоинтов не вводим).

### 5.2 Response-DTO и вложенные связи

Критерий из BEVN-101 (devlog: «запись и её прямые связи», каждая — только своими полями), как в эталоне, кроме PII и графа глубже
первого уровня. Граф ограничен DTO, поэтому REL-3 (обрыв ответа на глубине 32) невозможен по построению.

| Ресурс | Свои поля | Прямые связи | Эталон |
|---|---|---|---|
| Конференция (`GET` список/один, ответы `POST`/`PUT`) | `id, title, description, location, venue, startDate, endDate, status, maxAttendees, organizerName, website` | `sessions[]` (свои поля сессии), `registrations[]` (`id, registeredAt, status, conferenceId, attendeeId` — без `attendee`) | A01, A02 |
| Сессия (`GET /conferences/{id}/sessions`, `GET`/`PUT /sessions/{id}`, ответ `POST`) | `id, title, description, startTime, endTime, capacity, conferenceId, speakerId, roomId` | `conference`, `speaker`, `room` — свои поля; `null`, если связи нет | A06, A10, C04 |
| Регистрация (`GET /registrations`, ответ `/register`) | `id, registeredAt, status, conferenceId, attendeeId` | `conference` (свои поля), `attendee {id, firstName, lastName}` | D13 |
| Спикер (`GET /speakers`, ответ `POST`) | `id, firstName, lastName, bio, email, emailPublic` | `sessions[]` (свои поля) | A13 |

Пустые служебные поля вложенных объектов эталона (`"sessions": []`, `"registrations": []`, `"conference": null` внутри уже
вложенной записи — C04, A01) в новых DTO отсутствуют.

Запросы к БД — явные `select`-проекции под эти DTO, без `include` всего графа; число запросов на эндпоинт — константа,
не зависящая от числа записей (DoD-11, PERF-1).

### 5.3 Персональные данные (SEC-1, FE-5)

- **Участник**: email не отдаётся ни в одном ответе. Публичная форма — `{id, firstName, lastName}`, везде одинаковая, включая ответ
  `/register` (иначе ответ стал бы способом узнать данные по email). Имена публичны — FE-5 Fix «публично — максимум число
  регистраций или имена». UI покажет «—» вместо email (`ConferenceDetailPage.jsx:263`, `a.email || '—'`; по коду).
- **Спикер**: «email спикера — только если он явно публичный» (SEC-1 Fix). Новое поле `emailPublic` (`boolean`, по умолчанию
  `false`, необязательное в `POST /api/speakers`). При `false` ответ содержит `"email": null` — ключ есть всегда: форма стабильна,
  «нет email» и «скрыт» не различимы, `speaker.email &&` в UI работает (`SessionDetailPage.jsx:87`).
- Побочные эффекты: `PUT /speakers` нет — флаг задаётся только при создании; email спикера без флага хранится, но не возвращается
  ни одним эндпоинтом (описано в Swagger).

### 5.4 Вход и валидация (CORR-4, SEC-3, BEVN-107)

- Глобально `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true })`, без исключений в настройке.
  Неизвестное поле, `id`, вложенные `registrations`/`sessions` → `400` с указанием поля. У каждого поля DTO есть декоратор
  `class-validator` (иначе поле считается неизвестным).
- **Отдельные DTO для `POST` и `PUT`.** `PUT` — полная замена (CORR-5 Fix, вариант «все поля обязательны»): в теле обязаны быть все
  записываемые ключи, nullable-поля допускают `null`, отсутствие ключа → `400`. `PATCH` не вводится (DoD-2). Молчаливого обнуления
  (B11, C06) больше нет. Валидация — до изменения сущности (CORR-6).
- Правила полей (`400`): обязательные поля; лимиты длины (таблица «поле → лимит» из плана, общая с БД — 7.2); `email` — формат и **только ASCII**
  (`@IsEmail({ allow_utf8_local_part: false })`, домен ASCII/punycode, см. 6.4); `website` — URL; `endDate ≥ startDate` (равенство —
  однодневная конференция); `endTime > startTime`; `capacity` — целое ≥ 1 (строже аудита «неотрицательная»); `maxAttendees` — целое
  ≥ 1 или `null` (B09: `-3` → `200`).
- **`RegisterAttendeeDto`**: `firstName`, `lastName`, `email` — обязательные; `phone`, `company`, `dietaryRequirements` —
  необязательные строки с лимитом длины (пустая строка допустима); `sessionId` — `@IsOptional() @IsInt() @Min(1)` или `null`, без
  проверки существования. Описание в DTO и Swagger: «принимается, не сохраняется» (FE-3, первая альтернатива Fix).
- **`status` конференции на входе** (CORR-9): строго `UPCOMING | ACTIVE | COMPLETED | CANCELLED` или `null`, без нормализации
  регистра, иначе `400`. `CANCELLED` — отменить; `null` — не отменена. `UPCOMING`/`ACTIVE`/`COMPLETED` принимаются, только если
  совпадают со статусом, вычисленным из дат **этого же запроса** (6.1), иначе `400` «status is derived from dates; only CANCELLED can
  be set». В `PUT` ключ обязателен (иначе пропуск молча снимал бы отмену), в `POST` отсутствие = `null`.
- **id в пути**: строго `^[1-9][0-9]*$` и ≤ 2147483647, иначе `400` (`abc`, `0`, `007`, `+5`, ` 5`, `1e3`, `2147483648`).
- **Content-Type** для `POST`/`PUT`: `application/json` (с параметрами) и `application/*+json`; иначе `415` в едином формате.
  `text/json` больше не принимается (отличие от `ApiDocumentation.cs:18`).
- Read-only поля (`id` и др.) отвергаются, поэтому `GET` → `PUT` «как есть» не работает: клиент отправляет только записываемые поля.

### 5.5 Даты (CORR-8, частично)

- `startDate`, `endDate`, `startTime`, `endTime` — wall-clock места проведения, как сейчас: в ответе строго `YYYY-MM-DDTHH:mm:ss`
  без смещения и долей секунды (как эталон). На входе — только этот формат; `Z`, смещение, доли, несуществующая дата
  (`2025-02-30`) → `400`. Разбор — явно как UTC, проверка обратным преобразованием; формат — через `getUTC*`: результат не зависит
  от пояса сервера (старое поведение зависело — `ApiDocumentation.cs:21-27`).
- `registeredAt` — момент, ставит сервер: в ответе всегда ISO 8601 с `Z` и миллисекундами. Исправляет разный формат `POST`/`GET`
  (D04 `…13.1361921Z`, D13 `…13.136192`); в UI дата регистрации считается по реальному моменту (`ConferenceDetailPage.jsx:264`).
  Микросекунды теряются (Prisma — миллисекунды).
- Не делается: пояс конференции (IANA) и форматирование в поясе конференции во фронтенде — правка фронтенда и контракта.
- Почему не UTC + `Z` для расписания: `new Date()` в браузере сдвинул бы все времена на пояс пользователя
  (проверено агентом в соседней сессии (Node 22, V8), передано пользователем; для Asia/Bishkek — прямой прогон, для
  America/Los_Angeles — через `Intl` с `timeZone` (TZ на Windows не работает): `10:00Z` → 16:00 в Бишкеке, 02:00 в Лос-Анджелесе;
  `00:00Z` 5 марта → 4 марта в Лос-Анджелесе).

### 5.6 Ошибки (CFG-3, CORR-7, BEVN-104)

Тело любой ошибки, `Content-Type: application/json`:

```json
{ "statusCode": 400, "error": "Bad Request", "message": "Validation failed", "requestId": "…",
  "errors": [ { "field": "email", "messages": ["email must be an email"] } ] }
```

- `message` — всегда строка (BEVN-104: «structured JSON with a message»; поэтому не RFC 7807, где поля `message` нет).
- `errors` — только у `400` валидации и `422` по ссылкам; `field` — путь через точку.
- `requestId` генерирует сервер (входящий `X-Request-Id` игнорируется — клиент не подсовывает строки в логи); тот же id —
  в заголовке `X-Request-Id` и в строке лога. `500` — общая фраза, стек и детали только в лог.
- Один глобальный `ExceptionFilter`; CORS-заголовки есть и на 4xx/5xx (CFG-3: старый `500` без них → «Failed to fetch»).

| Код | Когда |
|---|---|
| 400 | валидация; битый или пустой JSON (B03, B04) — без текста парсера в `message`; плохой id; нарушение CHECK (`23514`, страховка: все CHECK повторяют правила входа; имя ограничения — в лог) |
| 404 | несуществующая сущность или родитель в URL — в т.ч. для списков (было `200 {"data":[]}` A07, `200 []` A09) и для `POST …/sessions`, `/register`; неизвестный маршрут; Swagger при выключенном флаге |
| 405 | неверный метод для существующего пути, с `Allow` (как A20) — **только если** это один небольшой middleware; иначе `404` и расхождение с A20 строкой в PR |
| 409 | повторная регистрация; мест нет; регистрация закрыта (статус не `UPCOMING`/`ACTIVE`); `PUT` конференции оставляет её сессии вне новых дат (в `message` — id таких сессий) |
| 413 | тело больше лимита парсера |
| 415 | Content-Type не JSON у `POST`/`PUT` (B02, C03, D12) |
| 422 | несуществующие `speakerId`/`roomId` (по FK, `P2003` по имени ограничения, без предварительного `SELECT`); сессия вне дней конференции; вместимость сессии больше вместимости зала |
| 503 | таймаут транзакции (`P2028`), ожидания блокировки (`55P03`) или запроса (`57014`, `statement_timeout`, раздел 8), заголовок `Retry-After: 1` — временная перегрузка, транзакция откатилась, повтор безопасен (`409` — про состояние ресурса, не подходит) |
| 500 | всё прочее |

Побочный эффект: UI показывает тело ошибки как есть (`api.js:10-11`) — пользователь увидит JSON вместо пустого текста /
`HTTP 404`. Без правки фронтенда не устранить; строкой в PR.

### 5.7 CORS (SEC-4)

Origin — список из `CORS_ORIGINS` (compose: `http://localhost:5173`); методы `GET, POST, PUT`; заголовки `Content-Type`;
`maxAge` 600 с; `exposedHeaders: X-Request-Id` (без него JS браузера заголовок не видит). `Location` не выставляется наружу —
UI его не читает, id есть в теле. Порт API 5000 остаётся опубликованным: `api.js:1` захардкожен (FE-1).

### 5.8 Swagger (SEC-5, DoD-10)

- Флаг `SWAGGER_ENABLED`: включается только точным значением `true`, по умолчанию выключен; в compose — `true`. Выключен — UI и
  JSON отвечают `404` в едином формате. README: в боевом запуске не включать.

## 6. Доменные правила

### 6.1 Статус конференции (CORR-10)

- Вычисляется из дат при каждом ответе: `UPCOMING` до начала дня `startDate`; `ACTIVE` с начала дня `startDate` до конца дня
  `endDate` (сравнение с `endDate` + 1 день: в данных `endDate` — полночь начала последнего дня, эталон `2025-03-06T00:00:00`);
  `COMPLETED` после. Хранится только признак отмены → `CANCELLED` перекрывает вычисленный.
- «Сейчас» — из инжектируемого `Clock` (в тестах — фиксированный).
- Ограничение: «сейчас» — UTC, даты — wall-clock без пояса, поэтому на границе дня погрешность до ±14 ч (строкой в PR; лечится поясом
  конференции — вне задачи).

### 6.2 Регистрация (CORR-1, CORR-2, CORR-3, REL-5)

Одна интерактивная транзакция (раздел 8), шаги:

1. `SELECT … FROM conferences WHERE "Id" = $1 FOR UPDATE` — параметризованный `$queryRaw` (tagged template, не
   `$queryRawUnsafe`); нет строки → `404`.
2. Открыта ли: статус `UPCOMING` или `ACTIVE`, иначе `409`.
3. Участник по нормализованному email: `INSERT … ON CONFLICT ("Email") DO NOTHING` + чтение (блокировка по конференции не защищает
   от одного нового email на **разные** конференции одновременно; Prisma `upsert` нативный `ON CONFLICT` использует не всегда —
   проверяется тестом гонки).
4. Уже зарегистрирован → `409`.
5. `count(CONFIRMED) < maxAttendees` (`null` — без лимита, B05), иначе `409`.
6. Вставка регистрации (`CONFIRMED`, `registeredAt` от сервера).

- `P2002` различается по ограничению: `(ConferenceId, AttendeeId)` → `409`; по email — не ошибка (шаг 3).
- Существующий участник с другим именем в форме: сохранённое имя остаётся, новое не пишется; ответ показывает сохранённое имя
  (CORR-3 Fix, вариант «сообщать клиенту»). Довод: без аутентификации (SEC-2) обновление по email позволило бы переписать чужое имя.
  Для UI невидимо: `RegistrationPage.jsx:31` ответ не читает, `ConferenceDetailPage.jsx:116` пишет его только в консоль.
- Email нормализуется (`trim` до проверки формата, затем `lower`) при записи и поиске; в БД и в ответах — нормализованный.
- Побочные эффекты: регистрации на одну конференцию сериализуются; на .NET Summit (`COMPLETED`) кнопка Register во фронтенде остаётся
  (`ConferenceDetailPage.jsx:245`), ответ `409` UI покажет сырым JSON.
- Риск для BEVN-202: `UNIQUE (ConferenceId, AttendeeId)` на всю таблицу не позволит повторную регистрацию после отмены
  (BEVN-202: «Cancelling a confirmed registration…»). Отмены сейчас нет — не меняем; частичный unique Prisma-схема не выражает,
  понадобится SQL в миграции. BEVN-202 также требует лимит на уровне сессии, а `sessionId` сейчас не хранится.

### 6.3 Сессии и конференции (CORR-4)

- `422`: день начала сессии ≥ день `startDate`, день окончания ≤ день `endDate` конференции (включительно); `capacity` сессии ≤
  `capacity` зала (равенство допустимо — сид на нём: 300/300, 80/80, 50/50).
- `409`: `PUT` конференции, после которого её сессии выпадают из новых дат; в `message` — их id.
- `POST`/`PUT` сессии и `PUT` конференции берут ту же блокировку строки конференции, что регистрация, — иначе параллельные `PUT`
  конференции и `POST` сессии пропустят нарушение.
- `conferenceId` сессии неизменяем (поле не входит в DTO `PUT` → `400`, C08).
- **Пересечения сессий в зале — не проверяются.** Причина — модель: зал не привязан к площадке (в сиде Hall A используют три
  конференции — Прага, Амстердам, Варшава), время — wall-clock без пояса; правило давало бы ложные конфликты. Нужен зал,
  принадлежащий площадке, — вне задачи.

### 6.4 Email: только ASCII

На ASCII `toLowerCase()` в JS и `lower()` в Postgres совпадают, поэтому CHECK в БД (7.2) не расходится с нормализацией в коде
(исключение — турецкая collation; [предполагаю], что у `postgres:14` по умолчанию `en_US.utf8`). Побочный эффект: адреса вида
`иван@пример.рф` не принимаются — строкой в PR.

## 7. Данные

### 7.1 Схема и имена

Prisma-схема с `@@map`/`@map`: таблицы (`conferences`, `sessions`, `speakers`, `rooms`, `attendees`, `registrations`) и колонки
(`"Id"`, `"ConferenceId"`, `"Email"`…) — **те же имена**, что создавал EF. Довод: шаги 4–6 раздела «Как воспроизвести» аудита
выполняют SQL по этим именам и после EXT-150 используются как регрессионные проверки. «Те же имена», не «та же схема» — типы и
ограничения меняются (7.2).

### 7.2 Ограничения

| Таблица | Изменения |
|---|---|
| все | PK `"Id"` — `GENERATED ALWAYS AS IDENTITY` (SEC-3: клиент не задаёт id; правка SQL миграции). Все строковые колонки — с лимитом длины (CORR-2, дополнение: сейчас `text` без лимита); лимиты задаёт единая таблица «поле → лимит» в плане, одна для БД (`@db.VarChar(n)`) и DTO (`@MaxLength(n)`) |
| `conferences` | `StartDate`/`EndDate` — `timestamp(0)` без пояса; `CHECK ("EndDate" >= "StartDate")`; `"Status"` — `text NULL`, `CHECK ("Status" = 'CANCELLED')` (вычисляемые статусы не хранятся — осознанное отличие от CORR-9 Fix «enum и в БД»); `"MaxAttendees" CHECK (>= 1)` |
| `sessions` | `StartTime`/`EndTime` — `timestamp(0)`; `CHECK ("EndTime" > "StartTime")`; `"Capacity" CHECK (>= 1)` |
| `speakers` | новая `"EmailPublic" boolean NOT NULL DEFAULT false` |
| `rooms` | `"Capacity" CHECK (>= 1)` |
| `attendees` | `"Email"` — `UNIQUE` и `CHECK ("Email" = lower(btrim("Email")))` |
| `registrations` | `"RegisteredAt"` — `timestamptz(3)`; `UNIQUE ("ConferenceId", "AttendeeId")`; `"Status" CHECK IN ('CONFIRMED')` |

- Индексы на FK — явные `@@index` (Prisma на Postgres их сам не создаёт; EF создавал — аудит, раздел «Производительность»):
  `sessions` (`ConferenceId`, `SpeakerId`, `RoomId`), `registrations` (`AttendeeId`); `registrations.ConferenceId` покрыт
  уникальным индексом. Без них — регресс списков против .NET.
- Имена ограничений и индексов задаются явно (`map:`) в стиле EF: `FK_sessions_speakers_SpeakerId`,
  `UQ_registrations_ConferenceId_AttendeeId`, `IX_sessions_ConferenceId`… — по ним фильтр разбирает `P2002`/`P2003`.
- FK — `ON DELETE RESTRICT` (эндпоинтов удаления нет).

### 7.3 Миграции (CFG-1)

- Одна начальная миграция на пустую БД; `prisma migrate deploy` — отдельный шаг перед стартом приложения (сервис `migrate`, 9.2),
  не в коде старта.
- Ручной SQL в миграции (identity, CHECK) не должен давать дрейфа: `prisma migrate diff` после применения — пустой.
- Непустая БД без истории миграций (старый том `EnsureCreated`) → Prisma отказывает (`P3005`) — проверяется тестом.

### 7.4 Существующий том

Старый том не мигрируется и не удаляется: в compose новое имя тома `postgres_data_v2`, `docker-compose up --build` на машине со
старым стеком поднимает чистую БД. README: старый том `<проект>_postgres_data` больше не используется, данные не переносятся,
удалить — `docker volume rm <проект>_postgres_data`.

### 7.5 Сид (CFG-5, CORR-10, DoD-3)

- Отдельная идемпотентная команда: таблица `conferences` пуста → залить, иначе ничего. В рабочем окружении запускается через `node`
  из собранного JS (`dist/prisma/seed.js`), без `tsx`/`ts-node`. В compose — после `migrate deploy`, до старта API; вручную — команда
  в README.
- Одна транзакция: старый `DataSeeder.cs` пишет за 4 `SaveChanges` (строки 18, 28, 71, 160) и проверяет только
  `Conferences.Any()` (строка 9) — сбой после спикеров дал бы дубли спикеров при следующем запуске [по коду].
- Содержимое — как `DataSeeder`, с изменениями:
  - .NET Summit 2024 — прошлые даты, как сейчас (пример закрытой регистрации);
  - CloudOps Days и Data & AI Forum — со сдвигом на +30 и +90 дней от даты запуска сида; сессии — вместе со своей конференцией,
    с тем же временем дня, длительностью и порядком дней (CORR-10 Fix «обновить даты демо-данных»);
  - `Status` конференций — `NULL` (статус вычисляется);
  - у трёх демо-спикеров `emailPublic = true` (страница сессии в UI не меняется);
  - залы получают id 1–4 на чистой БД.
- Ограничение: на долгоживущем томе демо «стареет» (через ~30 дней CloudOps Days станет `ACTIVE`, через ~90 регистрация на демо
  закроется); лечится пересозданием тома — в README.

## 8. Транзакции и конкурентность (DoD-7)

У каждой транзакции в коде — комментарий, какое состояние испортится без неё.

| Операция | Шаги в одной `$transaction` | Что без неё |
|---|---|---|
| `POST /register` | 6.2, шаги 1–6 | участник-сирота при ошибке (REL-5, D16); превышение лимита гонкой (CORR-1) |
| `POST`/`PUT` сессии | `FOR UPDATE` конференции → дни → вместимость зала → запись (FK → `422`) | параллельный `PUT` конференции пропустит сессию вне дат |
| `PUT` конференции | `FOR UPDATE` → сессии внутри новых дат (иначе `409`) → запись | частично применённое изменение (CORR-6, REL-4); сессии вне дат |
| сид | всё | дубли при повторном запуске (7.5) |

- `POST /conferences`, `POST /speakers` — одиночная вставка без транзакции.
- Таймауты: Prisma 7.10.0 по умолчанию `maxWait` 2000 мс, `timeout` 5000 мс [подтверждено: опубликованный `runtime/client.js`,
  `maxWait??2e3, timeout??5e3`]; задаются явно в `PrismaService`. В транзакциях с `FOR UPDATE` первым шагом
  `SET LOCAL lock_timeout = '2s'` — ожидание блокировки обрывается раньше таймаута транзакции. `P2028` и `55P03` → `503` (5.6).
- `statement_timeout` (ASYNC-5 Fix «тайм-ауты на запросы (`statement_timeout`)») — на соединение приложения, для **всех** запросов,
  не только транзакций: `DB_STATEMENT_TIMEOUT_MS`, по умолчанию 5000, передаётся параметром соединения пула. Отменённый сервером
  запрос (`57014` `query_canceled`) → `503` + `Retry-After: 1`. Соединения `migrate` и сида этот лимит не получают (миграции могут
  идти дольше).
- REL-1/REL-2/REL-4/PERF-2 не возникают по построению: нет общего контекста и трекера изменений; `PrismaService` — пул соединений,
  каждый запрос независим.

## 13. Изменения контракта для внешних клиентов (в PR и Swagger)

UI на них не опирается (проверено по коду фронтенда; в браузере — 11.5).

1. Сессии конференции — массив без `{data}` (C09).
2. `POST` → `201` + `Location` (конференция, сессия).
3. Неизвестные поля → `400` (было: молча игнорировались — `ApiDocumentation.cs:20`, `ConferencesController.cs:186`); например
   `conferenceId` в `PUT /api/sessions` (C08), `id` в `POST`.
4. `PUT` требует все записываемые ключи (было: пропущенные обнулялись — B11, C06).
5. `status` на входе — точный enum и согласованность с датами; `"active"` (B06, B10) → `400`; в ответе — вычисленный.
6. Даты расписания на входе — только без смещения; `registeredAt` — с `Z`, миллисекунды.
7. Email участников не возвращается; email спикера — только при `emailPublic`; новое поле `emailPublic`.
8. Регистрация: `409` на повтор, лимит, закрытую конференцию; `404` на несуществующую (было `500`, D16); email нормализуется;
   только ASCII.
9. Несуществующий родитель списков → `404` (было `200 []`); плохой id → `400` (было `404`/`500`); несуществующие
   `speakerId`/`roomId` → `422` (было `500`, C10).
10. Ошибки — JSON в едином формате (было: пустое тело или stack trace в Development).
11. `text/json` больше не принимается.
12. Swagger выключен без `SWAGGER_ENABLED=true`.
13. `405` может стать `404` (5.6).
